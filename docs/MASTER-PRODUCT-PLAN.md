## 1. تعريف المنتج النهائي

### ما هو Elkahmed Business؟

هو **منصة أعمال متكاملة لوكالة/مؤسسة رقمية صغيرة** تقدّم خدمات تطوير (مواقع، تطبيقات ويب، متاجر، لوحات تحكم، منتجات رقمية)، ويتكوّن من ثلاث طبقات مترابطة:

1. **موقع عام (Public Website)** — واجهة تسويقية: خدمات بأسعار، معرض أعمال، تواصل.
2. **بوابة عملاء (Client Portal)** — مساحة خاصة لكل عميل لمتابعة مشروعه: تقدّم، رسائل، ملفات، إشعارات.
3. **لوحة إدارة (Admin Dashboard)** — أداة داخلية للفريق: استقبال الطلبات، تحويلها لمشاريع، إدارتها حتى التسليم، وإدارة محتوى الموقع.

**إجابة صريحة على الأسئلة:** هو **مزيج** — موقع وكالة + منصة إدارة عملاء + بوابة إدارة مشاريع. وهو **ليس SaaS** في مرحلته الحالية: لا يوجد اشتراكات، ولا تعدد مستأجرين (multi-tenant)، ولا فوترة. المستأجر الوحيد هو المؤسسة نفسها.

### تحديد المنتج الموصى به

| البند | القرار |
|---|---|
| **تموضع المنتج** | "وكالة رقمية بموقع حيّ + بوابة عملاء شفافة" — نقطة البيع: العميل يرى تقدّم مشروعه لحظياً بدل البريد والمكالمات |
| **العملاء المستهدفون (Customers)** | أصحاب أعمال صغيرة/متوسطة (السوق المغربي/العربي أولاً — الأسعار بـ MAD افتراضياً) يطلبون مواقع وتطبيقات |
| **المستخدمون (Users)** | **زائر** (يستكشف ويطلب)، **عميل** (يسجّل ويتابع مشروعه)، **أدمن** (يدير الطلبات والمشاريع والمحتوى) |
| **القيمة الجوهرية** | قناة استقطاب → قبول → تنفيذ → تسليم في مكان واحد، بشفافية كاملة للعميل |
| **نموذج العمل** | خدمات بتسعير ثابت (من جدول `services`) + مشاريع بعرض سعر (Custom Quote) |
| **الاتجاه المستقبلي** | تشغيل الوكالة ذاتياً أولاً؛ تحويلها لـ SaaS (وكالات أخرى تستخدم المنصة) **قرار تجاري مؤجل** — انظر §25 |

### الفجوة بين المعمارية الحالية والمنتج المقصود

المعمارية (تطبيقان + Supabase) **تدعم المنتج بنيوياً**، لكن **نصف المنتج غير موصول**: موقع العملاء اليوم واجهة عرض ببيانات وهمية، ونموذج الطلب والمصادقة والبوابة stubs. كما أن مخطط قاعدة البيانات الحالي **لا يستطيع استضافة بوابة العملاء** (لا يوجد ربط بين `projects` والعميل، والرسائل والملفات محجوبة عن العملاء بسياسات RLS) — التفاصيل والهجرة المقترحة في §8 و§9.

## 4. رحلة المستخدم الكاملة (مصحّحة)

التدفق المقترح في الأصل صحيح بنيوياً لكن فيه خطأ ترتيب واحد: **طلب المشروع لا يتطلب حساباً** — النموذج عام (جدول `requests` يقبل INSERT من أي أحد بسياسة `requests: anyone can submit`). الحساب مطلوب فقط للبوابة. المسار المصحّح:

### زائر
```
الرئيسية → الخدمات → تفاصيل خدمة → معرض الأعمال → تفاصيل مشروع
→ طلب مشروع (بدون حساب) → تأكيد الإرسال
→ (اختياري لاحقاً) تسجيل حساب للانتظار في البوابة
```

### عميل
```
تسجيل حساب (profiles.role = 'client' تلقائياً — trigger موجود)
→ دخول → البوابة: "طلباتي قيد المراجعة" (بعد إصلاح المخطط)
→ الأدمن يقبل الطلب → يُنشأ مشروع مربوط بحساب العميل
→ العميل يرى المشروع في بوابته فوراً (Realtime)
→ متابعة التقدم (خط زمني) ↔ رسائل ↔ ملفات (روابط موقّعة)
→ إشعار عند كل تحديث حالة → التسليم → تقييم/أرشفة
```

### أدمن
```
دخول (middleware → requireAdmin) → لوحة Overview
→ طلب جديد يصل لحظياً (RequestsLive + جرس الإشعارات)
→ مراجعة → تغيير الحالة: reviewing → accepted/rejected
→ [المطلوب بناؤه] "تحويل لمشروع": ينشئ سجلاً في projects مربوطاً بالعميل
→ إدارة المشروع: حالة/تقدم ← رفع ملفات ← رسائل مع العميل
→ إشعار العميل تلقائياً بكل تغيير → وضع "Delivered" → إغلاق
```

**نقطة ناقصة في الحلقة اليوم:** لا يوجد زر/مسار "تحويل طلب مقبول إلى مشروع" في اللوحة — إنشاء المشاريع يدوي منفصل عن الطلبات (`projects/new/page.tsx` لا يقرأ من `requests` ولا يربط بعميل).

## 5. بوابة العملاء — المعمارية النهائية

> اليوم: `apps/customer/app/portal/` يقرأ `portalProjects` الوهمية. التصميم التالي هو الهدف.

### Dashboard البوابة
- ترحيب باسم العميل من `profiles.full_name` (استبدال "Ahmed" الثابت).
- بطاقات إحصائية **محسوبة** (اليوم مكتوبة يدوياً "3/1/8"): عدد المشاريع النشطة، الرسائل غير المقروءة، ملفات هذا الشهر.
- قائمة "مشاريعي" من `projects where client_id = auth.uid()` مع شريط تقدم وحالة وDeadline.
- مصدر البيانات: **Server Component** يستخدم Supabase server client (الجلسة من الكوكيز) — ليس browser client — حتى تعمل RLS على مستوى السيرفر.

### المعلومات المعروضة لكل مشروع
العنوان، نوع الخدمة، الحالة، نسبة التقدم، الموعد النهائي، آخر تحديث، التقنيات، الخط الزمني للمراحل، الرسائل، الملفات، التحديثات.

### نموذج الحالات (توحيد!)
اليوم هناك **ثلاثة نماذج حالة متضاربة**: `requests.status` (new/reviewing/accepted/rejected)، `projects.status` (default نصي حر 'Request Submitted')، و`PortalProjectStatus` في الواجهة (6 مراحل). القرار الموصى به — **فصل مرحلتَي البيع والتسليم**:

- **دورة الطلب (Sales pipeline)** في `requests`: `new → reviewing → accepted | rejected` (موجودة، صحيحة، تُترك).
- **دورة التسليم (Delivery)** في `projects.status` مع قيد CHECK موحّد:
  `Planning → Design → Development → Testing → Delivered`
  (يُضاف `progress` محسوب من المرحلة أو يُحدّده الأدمن — الحالية "Request Submitted/Discussion" مراحل بيع لا معنى لها على مشروع بدأ فعلاً).

### الرسائل
جدول `messages` المرتبط بـ `project_id`. العميل يرسل ويستقبل ضمن مشروعه فقط. Realtime على قناة `messages-project-{id}` (النمط مستخدم أصلاً في `ProjectDetail.tsx:254` — يُعاد استخدامه في البوابة).

### الملفات
سجلات `files` + الكائن في Bucket الخاص `elkahmed-files`. **العميل لا يصل للـ Bucket مباشرة أبداً** — يرى قائمة سجلات ملفاته (بعد إصلاح RLS)، وعند الضغط "تحميل" تُولَّد رابط موقّع صلاحيتها 5 دقائق (الدالة `createFileDownloadUrl` موجودة في `apps/dashboard/lib/storage.ts:89` وتُنقل للحزمة المشتركة).

### الإشعارات
جدول `notifications` (قراءة الذاتية موجودة ✅). Trigger جديد مقترح: عند تغيير `projects.status` أو رفع ملف → إشعار لـ `client_id`. جرس Realtime للعميل بنفس نمط `NotificationsBell.tsx`.

### النشاط/الخط الزمني
عرض مشتق: دمج (تغييرات الحالة + الرسائل + الملفات) مرتبة زمنياً — **بدون جدول جديد** في هذه المرحلة؛ إن لزم لاحقاً يُضاف جدول `activity_log`.

### الربط بـ Supabase — خلاصة
| الميزة | الجدول | RLS الجديدة المطلوبة | Realtime |
|---|---|---|---|
| مشاريعي | projects | clients read own (`client_id = auth.uid()`) | INSERT/UPDATE* |
| الرسائل | messages | clients read/insert own-project | INSERT (النمط جاهز) |
| الملفات | files | clients read own-project | UPDATE* |
| الإشعارات | notifications | ✅ موجودة (read own) | ✅ موجودة |

\* Realtime في Supabase يحترم RLS — أي subscription من العميل لن يستقبل شيئاً حتى تُضاف سياسات القراءة.

## 6. نظام طلب المشروع — المعمارية النهائية (تعريف فقط، بدون تنفيذ)

### التدفق الكامل
```
العميل/الزائر يملأ النموذج (apps/customer/app/request)
↓ تحقق في المتصفح (حقول إلزامية + بريد + طول الرسالة)
↓ INSERT via anon client (anon key + RLS = الحارس الحقيقي)
↓ requests (status='new' — السياسة تشترط ذلك حرفياً)
↓ trigger on_request_created (موجود ✅) → notifications لكل أدمن
↓ Realtime: قناة requests-live في لوحة الأدمن (موجودة ✅)
↓ الأدمن يراجع → reviewing → accepted/rejected (موجود ✅)
↓ [الجديد المطلوب] accepted → "Create project" (يفضَّل ربط الطلب بالمشروع)
↓ project جديد client_id = العميل (إن كان مسجلاً) أو دعوة بالبريد للتسجيل
↓ العميل يرى المشروع في البوابة + إشعار
```

### التعريف الدقيق

| البند | القرار |
|---|---|
| **حقول الطلب** | `name, email, phone, company?, need, message, budget?, deadline?` — مطابقة تماماً لعمود الجدول الحالي (لا تغيير مخطط مطلوب ✅) |
| **التحقق (Validation)** | متصفح: required + email regex + حد أقصى للرسالة (مقترح 2000) · قاعدة البيانات: NOT NULL موجودة · يُضاف لاحقاً rate-limit (§12) |
| **سجل قاعدة البيانات** | صف واحد في `requests` — لا جداول وسيطة |
| **الحالة** | `new → reviewing → accepted/rejected` (CHECK constraint موجود) |
| **إجراءات الأدمن** | تغيير الحالة (موجود) + **تحويل لمشروع** (ناقص) + حذف/أرشفة (ناقص) + ملاحظات داخلية (مؤجل — §25) |
| **رؤية العميل** | **غير ممكنة حالياً** — `requests` بلا `user_id` وبلا سياسة قراءة للعميل. المقترح (§8): عمود `profile_id?` اختياري + سياسة قراءة سطره فقط، أو الاكتفاء بإشعار بريدي (الأسهل والأنسب الآن) |
| **الإشعارات** | أدمن: trigger + Realtime (كاملة ✅) · عميل: بريد ترحيبي عبر Supabase Auth email (مؤجل) |
| **معالجة الأخطاء** | فشل الشبكة → رسالة inline + إبقاء البيانات · نجاح → رسالة نجاح + مسح آمن · لا alert() |
| **الأمان** | anon INSERT مقيّد بـ `status='new'` فقط (لا يستطيع كاتب خارجي حقن حالة) · RLS يمنع القراءة/التعديل من غير الأدمن · حماية سبام: honeypot field الآن، rate-limit لاحقاً |

## 7. لوحة الإدارة — الشكل النهائي

### Dashboard (Overview)
اليوم: جدول الطلبات + 4 عدادات (كلها للطلبات). النهائي: صفّان — عدادات تشغيلية (طلبات جديدة، مشاريع نشطة بحسب الحالة، مكتملة هذا الشهر، رسائل غير مقروءة) + جدولا الطلبات الحية والنشاط الأخير. لا "Revenue" — لا يوجد حقل دخل في المخطط ولا فوترة (قرار §25).

### Requests
موجود: قائمة حية بـ Realtime + تغيير حالة inline. ناقص: صفحة تفاصيل الطلب (الرسالة كاملة تُعرض مقطوعة `line-clamp-2` اليوم)، زر **تحويل لمشروع مقبول**، تأكيد قبل rejected، بحث/تصفية.

### Projects
موجود: إنشاء/قائمة/تفاصيل + رسائل + ملفات + رفع صور. ناقص: **ربط بالعميل (client_id)**، شريط تقدم رقمي (عمود `progress`)، تحديث حالة منسدل موحّد على enum §5، إشعار العميل التلقائي عند التغيير، تمييز "معرض عام" عن "مشروع عميل".

### Services
موجود وشبه مكتمل: تعديل العنوان/الشعار/الوصف/الصورة/السعر/الخصم/العملة (`ServiceEditor.tsx`). ناقص: إنشاء خدمة جديدة وحذف/إخفاء (visibility) — اليوم تعديل فقط.

### Portfolio (معرض الأعمال) — وحدة جديدة بالكامل
اليوم معرض الموقع mock ثابت في الكود. النهائي: جدول `portfolio_items` + شاشة إدارة (صور من Assets bucket، دراسة حالة، تقنيات، مشروع مميز). تفاصيل الهجرة في §8.

### Settings
موجود: اسم الشركة، بريد، هاتف، عنوان، ساعات العمل، شعار، روابط اجتماعية (jsonb). كافٍ للمرحلة الأولى؛ يُضاف لاحقاً: لغة افتراضية وSEO افتراضي.

### Proposed Migration 0002 — client ownership & portfolio

**المشكل:** بوابة العملاء مستحيلة حالياً: (1) `projects` عامة القراءة بالكامل — تسريب بيانات عملاء محتمل، (2) لا ملكية `client_id`، (3) `messages`/`files` محجوبة عن العملاء، (4) معرض الأعمال العام ممزوج مفاهيمياً مع مشاريع العملاء.

**التغيير المقترح:**
1. `alter table projects add column client_id uuid references profiles(id)` + عمود `visibility text default 'private' check (visibility in ('public','private'))` + `progress int default 0`.
2. **إسقاط** سياسة `projects: public read` واستبدالها بسياستين: قراءة عامة فقط `where visibility='public'` وقراءة عميل `where client_id = auth.uid()`.
3. قيد CHECK جديد على `projects.status` (enum مراحل التسليم من §5).
4. سياسات جديدة: `messages`/`files` — عميل يقرأ/يكتب (رسائل فقط) ضمن `exists (select 1 from projects where id = project_id and client_id = auth.uid())`.
5. جدول جديد `portfolio_items` (slug, title, category, summary, challenge, solution, features, technologies, images, featured) — قراءة عامة/كتابة أدمن. **بديل أرخص:** إعادة استخدام `projects` نفسها مع `visibility='public'` — مرفوض لأن بيانات معرض التسويق (challenge/solution/features) ستخنق جدول التسليم بأعمدة كثيرة فارغة.
6. Trigger: `on_project_status_changed` → إشعار `client_id`؛ `on_file_uploaded` → إشعار `client_id`.
7. فهارس: `projects(client_id)`, `requests(status, created_at desc)`, `messages(project_id, created_at desc)`, `files(project_id)`, `notifications(user_id, read)`.

**السبب:** بدون هذه التغييرات لا توجد بوابة عملاء ولا عزل بين العملاء (§9) — هي شرط أساسي لكل مرحلة P0.

**المخاطر:** إسقاط `projects: public read` سيكسر أي جزء من الموقع يفترض قراءة عامة (اليوم لا شيء — الموقع mock، لذا **الآن هو التوقيت الأمثل قبل أول نشر**) · التراجع بعد نشر بيانات حقيقية أصعب (نقل المشاريع القائمة إلى visibility مناسب).

**البدائل:** (أ) الإبقاء على القراءة العامة والاكتفاء بعدم عرض الحساس — مرفوض: أمنياً غير مقبول. (ب) جدول منفصل `client_projects` تماماً — مضاعفة صيانة الرسائل/الملفات المرتبطة. (ج) Postgres RLS وحده بعمود client_id بدون visibility — يفقد معرض الأعمال العام. **التوصية: الخطة الرئيسية (1–7).**

**الحالة: ⏳ بانتظار الموافقة — لم يُنفذ شيء.**

## 9. أمان تعدد العملاء (Multi-Client Security)

### المبدأ: العميل A لا يرى شيئاً من العميل B — كفريضة قاعدة بيانات لا كمنطق تطبيق

**ما هو مضمون اليوم (ممتاز):**
- كل استعلامات اللوحة تمر بمفتاح anon + JWT الجلسة — **مفتاح service_role غير مستخدم إطلاقاً** (موثّق صراحة في `apps/dashboard/lib/supabase/server.ts:8-9`)، فلا يمكن لأي مسار في التطبيق تجاوز RLS.
- `notifications`: قراءة/تحديث `user_id = auth.uid()` فقط ✅.
- `profiles`: قراءة ذاتية + قراءة شاملة للأدمن فقط؛ **الترقية الذاتية لدور admin مستحيلة**: trigger الإنشاء يفرض `'client'` وسياسة التحديث الذاتي تشترط `role = 'client'` (لا يمكن تغيير الدور نفسه) ✅.
- التخزين: Assets عام للقراءة/كتابة أدمن؛ Files خاص بالكامل — التنزيل عبر روابط موقّعة فقط ✅.
- الدفاع الطبقي للأدمن: middleware (جلسة) → `requireAdmin` على السيرفر قبل أي استعلام → RLS على القاعدة → `ensureAdmin` في المتصفح (تحسين تجربة لا أمن) ✅.

**ما هو مكسور/ناقص اليوم (صريحاً):**
1. `projects: public read` — **أي زائر مجهول يمكنه قراءة كل المشاريع** بما فيها عميلها وموعدها وصورها عبر واجهة Supabase REST. اليوم البيانات تجريبية فلا ضرر فعلي، لكنه ثغرة بمجرد أول عميل حقيقي.
2. `messages`/`files`: أدمن فقط — أي أن "العزل" اليوم موجود بالصدفة (لأن العميل لا يستطيع قراءة شيء أصلاً). عند بناء البوابة يجب إضافة سياسات **مقيّدة بمشروع العميل** (كما في §8.4) — عندها فقط يصبح العزل قصدياً ومُختبَراً.
3. `requests`: إدراج عام بلا حدود — لا rate limiting ولا captcha: قابل لإغراق جدول الإشعارات (كل INSERT يولّد إشعاراً لكل أدمن عبر trigger). خفيف المخاطر الآن، يعالَج بـ honeypot + حد إرسال.
4. **Realtime يحترم RLS**: إضافة جداول لـ publication (`0001_dashboard_module.sql:285-287`) تعني أن العميل المشترك على قناة messages لن يستقبل شيئاً حتى تُضاف سياسته — سلوك صحيح، لكن يجب اختباره صراحة (§22).
5. `storage.objects` سياسات عامة على مستوى objects: سياسة "assets: public read" تستخدم `bucket_id = 'elkahmed-assets'` بدون قيود مسار — كافٍ الآن؛ عند نمو المجلدات يُفضّل `db.prefix` policies.

### مصفوفة الوصول النهائية (بعد الهجرة المقترحة)

| المورد | زائر | عميل (A) | أدمن |
|---|---|---|---|
| settings | قراءة | قراءة | كتابة |
| services | قراءة | قراءة | كتابة |
| portfolio_items | قراءة | قراءة | كتابة |
| projects | قراءة العامة فقط (visibility=public) | **مشروعه فقط** | الكل |
| requests | INSERT (status='new') فقط | مشروعه فقط (اختياري) | الكل |
| messages | — | مشروعه: قراءة+إرسال | الكل |
| files | — | مشروعه: قراءة سجل + رابط موقّع | الكل + رفع |
| notifications | — | خاصته فقط | خاصة به + إدراج لأي أحد (للأدمن) |

| Files bucket | — | **لا وصول مباشر** — رابط موقّع ≤5 دقائق | كامل |

### التحقق من Realtime والروابط الموقّعة
- Realtime: اختبار سلبي إلزامي — اشتراك بجلسة عميل A على قناة مشروع عميل B يجب ألا يستلم شيئاً (§22).
- الروابط الموقّعة: توليدها من السيرفر (server component/route) بعد التحقق أن `project.client_id = auth.uid()`؛ الصلاحية 300 ثانية (القيمة الحالية الافتراضية في `storage.ts:92` — مناسبة، لا تُرفع).

## 10. معمارية Supabase النهائية

```
Supabase Auth (email/password · جلسات عبر كوكيز @supabase/ssr)
   ↓ trigger on_auth_user_created
profiles (دور client تلقائياً · admin يدوياً من لوحة Supabase فقط)
   ↓ موافقة الأدمن
requests (INSERT عام مقيّد) ──trigger──→ notifications (لكل أدمن) ──Realtime──→ لوحة الأدمن
   ↓ accepted (قرار بشري)
projects (client_id · visibility · status/progress)
   ├─→ messages (عميل↔أدمن · Realtime للطرفين)
   ├─→ files (سجل) ──→ Storage/elkahmed-files (خاص · روابط موقّعة)
   └─→ triggers تغيير الحالة/رفع ملف ──→ notifications (للعميل)
services / portfolio_items / settings ──(قراءة عامة للموقع، كتابة أدمن)──→ الموقع العام
Storage/elkahmed-assets (عام) ← رفع من اللوحة ← عرض في الموقع والمعرض
```

**توزيع المسؤوليات:**

| الطبقة | مسؤولياتها | ممنوعاتها |
|---|---|---|
| **قاعدة البيانات (Postgres)** | RLS كخط الدفاع الوحيد الحقيقي · Triggers (profile تلقائي، إشعارات) · CHECK constraints · الفهارس | منطق عمل معقد |
| **السيرفر (RSC/Route Handlers)** | `requireAdmin` · توليد الروابط الموقّعة بعد فحص الملكية · قراءات البوابة بجلسة العميل | استخدام service_role · قراءات تتخطى RLS |
| **المتصفح (Client)** | Realtime subscriptions · تحسين تجربة (تحقق مبكر، ensureAdmin) · رفع ملفات عبر عميل مصادَق | أي قرار أمني |

**PostgreSQL:** مخطط `public` فقط، صف واحد في settings، UUID للمشاريع وBIGINT identity للبقية — مناسب. **Functions:** `handle_new_user`, `notify_admins` + المقترح `notify_client`. لا حاجة لEdge Functions في هذه المرحلة (كل شيء يتمكن عبر RSC + RLS).

## 11. Realtime — أين يوجد ولماذا (وأين لا يوجد)

المبدأ: **Realtime للحدث الذي يستحق مقاطعة المستخدم فقط** — لا اشتراكات "احتياطية".

| الحدث | القناة | الجدول/Event | المستمع | رد فعل الواجهة | الحالة |
|---|---|---|---|---|---|
| طلب جديد | `requests-live` | requests/INSERT | لوحة الأدمن | صف جديد بأعلى الجدول + عدادات | ✅ موجود (`RequestsLive.tsx:26`) |
| رسالة جديدة (مشروع) | `messages-project-{id}` | messages/INSERT | ProjectDetail (أدمن) — **لاحقاً بوابة العميل بنفس النمط** | إلحاق الرسالة فوراً | ✅ أدمن / ⬜ عميل |
| إشعار جديد | `notifications-{userId}` | notifications/INSERT | جرس الأدمن — لاحقاً جرس العميل | شارة عدّاد + قائمة | ✅ أدمن / ⬜ عميل |
| تغيّر حالة مشروع | `projects-client` (جديد) | projects/UPDATE | بوابة العميل | تحديث الشارة والخط الزمني | ⬜ مقترح |
| رفع ملف | عبر إشعار notifications | files/INSERT→trigger | جرس العميل | إشعار فقط — **لا** قناة ملفات مباشرة (غير ضروري) | ⬜ مقترح |

**قرارات صريحة:** لا Realtime على `services`/`settings`/`portfolio` (بيانات شبه ثابتة — revalidate كافٍ) · لا Realtime على `profiles` · كل قناة تُنشأ بـ projectId/userId محدد وتُزال عند unmount (النمط الصحيح مستخدم أصلاً في الكود مع `removeChannel`).

## 12. التخزين (Storage) — معمارية الملفات النهائية

### أصول عامة — `elkahmed-assets` (عام)
- **المحتوى:** صور الموقع (شعار، أغلفة خدمات، صور معرض الأعمال).
- **السياسات (موجودة ✅):** قراءة عامة للجميع، كتابة أدمن فقط.
- **الرفع:** من لوحة الأدمن فقط عبر `uploadToBucket` مع تطبيع أسماء الملفات (`safeFileName` يمنع path traversal ✅).
- **العرض:** `getPublicUrl` مع `cacheControl: 3600`.

### ملفات العملاء — `elkahmed-files` (خاص)
- **المحتوى:** عقود، مستندات، تسليمات — **لا تُعرض أبداً كروابط عامة**.
- **السياسات (موجودة ✅):** أدمن فقط على مستوى الكائنات.
- **تنزيل العميل (بعد الهجرة):** البوابة تطلب عبر route handler → السيرفر يتحقق `client_id = auth.uid()` → `createSignedUrl(path, 300)` → رابط يموت خلال 5 دقائق. **لا رفع من العميل في هذه المرحلة** (يقلل سطح الهجوم؛ إن لزم لاحقاً: سياسة insert مقيّدة بنوع/حجم).
- **الحدود المقترحة (سياسة تطبيق عند الرفع من اللوحة):** أنواع: jpg/png/webp/svg للم/general؛ pdf/docx/xlsx/zip للملفات الخاصة · حجم أقصى: 10MB للأصول، 50MB للملفات · (حدود حجم الملف الحالية: **غير مفروضة — فجوة صغيرة تُعالج في ImageUploader**) · **لا** نوع قابل للتنفيذ (exe/bat).

## 14. معمارية الواجهة (Frontend) — الشكل النهائي

### `apps/customer` — موقع العملاء
- **الصفحات:** عامة (home/about/contact/services+slug/projects+slug/request) + `(auth)` (login/register/forgot) + `portal` (لوحة + مشروع). البوابة تُحرس بـ middleware جديد (نفس نمط لوحة الأدمن) يسمح بأي جلسة (client أو admin).
- **المكوّنات:** موجودة ومكتملة بصرياً (Button, ServiceCard, ProjectCard, Timeline, StatusBadge...).
- **Lib:** `lib/data.ts` يبقى **نقطة الالتقاء الوحيدة** (التصميم الحالي صحيح) — تُستبدل أجساد الدوال: mock → استعلامات Supabase. **تصحيح مهم:** `getSiteSettings` تستخدم اليوم browser client داخل Server Components — تُحوَّل إلى server client حتى تعمل RLS/جلسة السيرفر بشكل صحيح.
- **Server/Client:** الصفحات RSC افتراضياً؛ `"use client"` فقط للنماذج وRealtime.

### `apps/dashboard` — لوحة الإدارة

## 15. تدفقات البيانات (Data Flows)

**تسجيل دخول (لوحة):** دخول بريد/كلمة مرور → Supabase Auth → كوكيز جلسة (@supabase/ssr) → middleware يجدد ويصدّ غير المسجل → `(protected)/layout` → `requireAdmin` → profiles.role=admin؟ → DashboardShell : AccessDenied. (كل الخطوات موجودة ✅)

**طلب مشروع جديد:** الزائر → RequestForm (تحقق متصفح) → anon INSERT في requests → RLS `anyone can submit` → trigger `on_request_created` → notify_admins → notifications → Realtime قناة `requests-live` → RequestsLive يضيف الصف + عدادات.

**إنشاء مشروع:** الأدمن → projects/new → ensureAdmin (متحصفح) → INSERT → RLS admins write → القائمة تُحدَّث. *(اليوم بلا ربط بعميل — بعد الهجرة: client_id إلزامي + إشعار للعميل).*

**تحديث مشروع:** الأدمن → ProjectDetail → UPDATE status → RLS → *(مستقبلاً)* trigger حالة → إشعار عميل → Realtime بوابة العميل → تحديث الخط الزمني.

**رسالة:** مرسل (أدمن أو عميل) → INSERT messages → trigger إشعار للطرف الآخر → Realtime قناة المشروع → إلحاق فوري في الواجهتين.

**رفع ملف:** الأدمن → اختيار ملف → uploadToBucket على elkahmed-files → INSERT سجل في files → *(مستقبلاً)* trigger إشعار عميل → العميل يرى الملف → طلب تنزيل → route handler يتحقق الملكية → createSignedUrl(300s) → تنزيل.

**إشعار:** trigger → notifications → Realtime قناة user → جرس → mark read (سياسة تحديث ذاتي).

**تحديث خدمة:** الأدمن → ServiceEditor → UPDATE services → RLS admins write → الموقع يقرأ بـ ISR/revalidate → صفحة الخدمة تتحدث.

**تحديث معرض:** الأدمن → رفع صور إلى assets (عام) → INSERT/UPDATE portfolio_items → الموقع يعيد التوليد → صفحة معرض/دراسة حالة.

## 19. الأداء — المخاطر مرتبة بالأثر

1. **(أثر مرتفع · سيظهر عند التوصيل)** استعلامات Supabase من RSC بلا تخزين مؤقت: صفحات الخدمات/المشاريع ستتحول من static إلى ديناميكية. **الحل:** ISR (`export const revalidate = 300`) + `revalidateTag` عند التحديث من اللوحة — يحمي SEO وسرعة الصفحة.
2. **(أثر مرتفع)** لا استخدام لـ`next/image` إطلاقاً اليوم (لا `<img>` ولا Image — الصور placeholders/tailwind gradients). عند إدخال صور حقيقية من Storage: `next/image` مع `remotePatterns` لنطاق Supabase + sizes مسؤولة.
3. **(متوسط)** `getSiteSettings` تُستدعى من كل صفحة (Navbar/Footer) وتفتح استعلاماً كل مرة — الحل: React `cache()` حولها في RSC + ISR.
4. **(متوسط)** جلب من المتصفح حيث يكفي السيرفر: البوابة الحالية browser client — التحويل لـ server client يقلل round-trips ويصلح RLS.
5. **(متوسط · DB)** لا فهارس غير المفاتيح الأساسية — استعلامات اللوحة (`order by created_at desc`, تصفية status) ستبطئ مع النمو. الحل: فهارس §8.7 (رحلة مقترحة، بموافقة).
6. **(منخفض)** Bundle: lucide-react imports بشكل named — جيد؛ التطبيقان نحيفان (~لا مكتبات ثقيلة) ✅.
7. **(منخفض)** Realtime: 3 قنوات فقط بمدى حياة صحيح ✅ — لا تحسين مطلوب الآن.

## 21. التدويل (i18n)

المحتوى الحالي كله بالإنجليزية، والأسعار MAD، والسوق الظاهر مغربي/عربي — **قرار i18n لا يمكن تركه معلقاً**:

- **اللغات:** العربية (ar) + الإنجليزية (en) أساساً؛ الفرنسية (fr) خيار ثانٍ للسوق المغربي. **القرار: البدء بـ en فقط في الإطلاق، ثم ar كإضافة مخططة (وليس العكس)** — لأن كل المحتوى والبيانات التجريبية en بالفعل، وar يتطلب RTL كامل.
- **الافتراضية:** en في الإطلاق → ar تُضاف كلغة كاملة بعد الإطلاق.
- **RTL/LTR:** عند إضافة ar: `dir="rtl"` على `<html>` بمستوى الصفحة + منطق Tailwind logical properties (`ms-/me-` بدل `ml-/mr-`) — **قرار تنفيذي فوري:** كل كود جديد يستخدم logical properties من الآن لتفادي إعادة كتابة لاحقة.
- **البنية:** `next-intl` (الأنضج مع App Router) · ملفات `messages/{en,ar,fr}.json` · الترجمات في الكود، ومحتوى DB (services/portfolio) بمعالجة لاحقة إما أعمدة مترجمة (title_ar...) أو جدول ترجمات — **يُقرر في وقتها عند وجود طلب فعلي**.
- **الروابط:** `/en/...` و`/ar/...` مع بقاء الافتراضية بلا بادئة.
- **SEO:** hreflang + sitemap لكل لغة + canonical.
- **اللوحة والبوابة:** اللوحة (أدمن) en دائماً · البوابة تتبع لغة الموقع.

- **PHASE 3 (الهجرة):** الهجرة idempotent · عميل A لا يقرأ مشروع B (اختبار SQL سالب) · لا انحدار في اللوحة · rollback مُجرَّب على نسخة staging.
- **PHASE 4 (بوابة):** عميل حقيقي يسجل → يدخل → يرى مشروعه فقط · رسائل تعمل بالاتجاهين لحظياً · تنزيل ملف برابط موقّع يموت بعد 5 دقائق · غير المسجل يُصدّ · مُختبَر جوالاً.

- **PHASE 7:** كل اختبارات RLS السالبة خضراء في CI.
- **PHASE 8:** sitemap.xml وrobots.xml صحيحان · OG يُعاين بنجاح (validator) · pagespeed أخضر.
- **PHASE 9:** builds خضراء في CI · نطاقات تعمل بـHTTPS · خطة نسخ احتياطي مؤكدة · دخول أول عميل حقيقي ناجح من الجوال.

## 25. ما لا يُبنى الآن (إلزامي)

| الميزة | القرار | السبب |
|---|---|---|
| مدفوعات/فوترة | **مؤجل** | لا نموذج اشتراكات؛ الفوترة تحدث خارج المنصة (تحويل/عقد). بناؤها الآن يضيف PCI/ضرائب/أخطاء بلا قيمة فورية |
| CRM متقدم | **مؤجل** | requests+notifications تغطي حجم وكالة صغيرة؛ لن يستفيد أحد من pipeline معقد قبل 50+ طلب شهرياً |
| Analytics متقدم | **مؤجل** · الأسهل: Vercel Analytics/Plausible بنقرة | لوحات مخصصة تحتاج بيانات تراكمية غير موجودة بعد |
| Multi-tenant SaaS | **مؤجل بصرامة** | يتطلب عزل بيانات لكل وكالة (RLS by tenant_id أو schema لكل مستأجر) — إعادة معمارية كاملة قبل التحقق من الطلب التجاري |
| ميزات AI | **مؤجل** | لا حالة استخدام مُثبتة في التدفق الحالي |
| تطبيقات موبايل | **لا** | البوابة واللوحة ويب متجاوب يكفيان تماماً |
| رفع ملفات من العميل | **مؤجل** | يوسع سطح الهجوم (تخزين+تحقق أنواع) بلا حاجة تشغيلية ملحّة الآن |
| ملاحظات داخلية على الطلبات | **مؤجل** | عمود notes بسيط يُضاف في هجرة لاحقة عند الحاجة الفعلية |
| Edge Functions | **لا** | كل المسارات ممكنة بـRSC+RLS وtriggers |
| i18n كامل (ar/fr) | **مؤجل منظم (§21)** | يُطبع بعد إطلاق en — ليس "مستقبلاً غامضاً" بل إصدار مخطط |
